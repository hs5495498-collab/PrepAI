# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PrepAI — a static interview-practice dashboard prototype. Plain HTML/CSS/JS only: no build step, no package manager, no framework, no bundler, no CDN scripts except the Inter Google Font (which degrades to system fonts if offline).

## Running / testing

There is no build or test tooling. To work on the app, open any `.html` file directly in a browser (e.g. `index.html`), or serve the folder with any static file server. There is no lint/build/test command to run — verify changes by loading the page in a browser.

## Architecture

Every screen is a standalone HTML file that loads these scripts in a fixed order:

```
js/icons.js → js/data.js → js/chart.js → [js/api.js] → js/pages.js → js/app.js
```

`js/api.js` is optional and only included on pages that actually talk to the backend (currently `practice.html`, `settings.html`, `results.html` — added in Phase 8 for the "Evaluate with AI" button — `analytics.html`, added in Phase 9 for personalized recommendations — and `history.html`, added in Phase 10 for account history). Pages that don't need it keep the original five-script list.

- **`js/data.js`** — the single source of truth. Defines `window.PREP`, with the sample dataset (`attempts`, `skills`, `achievements`, `actions`, `feedback`, `details`, `bank`) and derived helpers (`completed()`, `result()`, `changeFor()`, `achievementState()`, etc). Every number rendered anywhere in the UI is computed from this object — there is no other data source. It also loads/persists real completed demo attempts (`P.addDemoAttempt`, see "Data model notes" below).
- **`js/api.js`** — `window.PREP_API`: a small fetch wrapper for the FastAPI backend (`backend/`), pointed at `http://127.0.0.1:8000`. Every call resolves (never rejects) to `{ ok, status, data }`; `status === 0` means a network failure/timeout rather than a real HTTP response, so callers can tell "backend unreachable" apart from a real 4xx/5xx. This is the only place the backend URL is hardcoded. Since Phase 7 it also sends `credentials: 'include'` (so the login session cookie flows both ways) and attaches an `X-CSRF-Token` header, read from the non-HttpOnly `prepai_csrf` cookie, on every non-GET request — see `backend/README.md`'s "Authentication and accounts" section for why.
- **`js/pages.js`** — defines `window.PREP_PAGES`, a map of page-name → render function (`dashboard`, `practice`, `history`, `analytics`, `achievements`, `plan`, `results`, `settings`). Each function reads from `window.PREP`, builds HTML strings, and injects them into the current page's DOM. No templating engine — just string concatenation with a local `esc()` helper for untrusted text.
- **`js/app.js`** — the app shell. On `DOMContentLoaded` it: applies saved display settings, builds and injects the sidebar `<nav>` (the `NAV` array is the single list of screens/labels/icons), wires the mobile menu, hydrates inline icons, then looks up `body[data-page]` and invokes the matching function from `window.PREP_PAGES`.
- **`js/chart.js`** — `window.createChart(container, options)`: a dependency-free inline-SVG line chart with trend line, markers, and tooltips. Returns `{ update(partial) }` so pages can redraw on filter changes (see `pages.analytics`).
- **`js/icons.js`** — `window.icon(name, size)` returns inline SVG markup; `window.hydrateIcons(root)` fills any `[data-icon]` element.
- **`css/styles.css`** — the entire design system (colors, type, components, responsive rules) in one file. No CSS preprocessor.

### Page wiring convention

Each HTML file's `<body>` carries two data attributes that drive `app.js`:
- `data-page="<name>"` — selects which function in `window.PREP_PAGES` to run.
- `data-nav="<file>.html"` — marks the matching sidebar link `aria-current="page"`.

When adding a new screen: create the HTML file with these attributes and the script tags (add `js/api.js` only if that page calls the backend), add an entry to the `NAV` array in `js/app.js`, and add a render function to `js/pages.js` under the matching key.

### Data model notes

- An attempt's `status` is one of `completed | incomplete | missed`. Only `completed` attempts have a `score`; incomplete/missed attempts are never scored (by design, not a bug).
- `P.ref` (in `data.js`) is the latest attempt's date, and all "last N days" range filters (history, analytics) count backwards from it rather than from `Date.now()` — the prototype's dataset is meant to look current relative to itself.
- Settings (`settings.html`) persist to `localStorage` under `prepai.settings`; `window.PREP_SETTINGS()` reads them and `window.applyDisplaySettings()` applies text-size/reduce-motion globally.
- Completed/incomplete practice attempts persist to `localStorage` under `prepai.demoAttempts` via `P.addDemoAttempt`/`loadDemoAttempts` in `data.js`. A completed attempt's `source` field is `'backend'` if its answers were actually submitted to the FastAPI backend during that session, or `'offline'` if the session ran entirely in the browser (backend unavailable, or the user chose "Continue in Offline Demo Mode"). As of Phase 6 the backend persists sessions in a real SQLite database (`backend/data/prepai.db`) and they survive a backend restart, but `localStorage` is still the only thing the *frontend* reads for history/analytics/achievements — the backend database and `localStorage` are two separate stores, not synced with each other.

### Known prototype limitations (see README.md)

- The microphone/waveform UI in `practice.html` is visual only — no real recording. Hook up `MediaRecorder`/speech-to-text inside `setRecording()` in `pages.js`.
- Interview *questions* can be AI-generated (see `backend/ai_provider.py`), and submitted *answers* can be AI-evaluated (see `backend/evaluation_provider.py`, Phase 8) — two completely independent features, each off by default behind its own flag (`AI_QUESTIONS_ENABLED` / `AI_EVALUATION_ENABLED`) in `backend/.env`. See `backend/README.md`. The practice-interview "demo score" (`demoScore()` in `pages.js`, always labeled "(demo)") is unaffected either way — it is never replaced by an AI evaluation; the AI evaluation is a separate, additional, explicitly-requested result shown per-question on `results.html` via an "Evaluate with AI" button, never shown automatically.
- A session's `question_source` (`"ai"` or `"fixed"`) is shown live during the interview (next to the question counter) but is not persisted into `localStorage` history — only the existing `source` (`backend`/`offline`) field is. A completed backend attempt's `sessionId` and each `qa[].id` *are* persisted (Phase 8) — that's what the results page's evaluate button uses; attempts from before Phase 8, or made entirely offline, lack these and simply show no evaluate button.
- Accounts (Phase 7, see `backend/README.md`) are optional and email+password only — no social login, email verification, or password reset. Logging in only changes one thing: interviews you create afterward get tied to your account (only you can read/answer/complete them); interviews created anonymously keep working exactly as before and are never auto-assigned to an account. The Settings page's "Account" section (`#account-section`) is the actual login/registration form — every other page's topbar now also carries a small "Log In"/account-email link (added in `app.js`, only rendered on pages that load `js/api.js`) that jumps straight to `settings.html#account-section`, so a logged-out user always has an immediate, visible way to reach it instead of needing to already know Settings has it.
- There is still no frontend feature to look up an old in-progress session after a page refresh, even though its data does survive on the server (since Phase 6, now also true for owned interviews).
- `analytics.html`'s new "Personalized Recommendations" section (Phase 9) is unrelated to the existing sample-data-driven "What to Focus On Next" list right above it on the same page — that list still reads from the static `P.skills` dataset exactly as before (untouched this phase). The new section instead calls `GET /api/recommendations`, a deterministic rule engine (`backend/recommendations.py`) over the signed-in account's own real evaluated answers - it makes no AI calls itself and requires being logged in (no anonymous equivalent). It loads automatically on page view, unlike the per-question evaluate button, because it has no cost.
- `history.html` (Phase 10) now has **two separate, clearly-labeled sections**: "Your Account History" (new, calls `GET /api/interviews`, requires login, real cross-device data) and "Local Browser History (This Device Only)" (the original `P.attempts`/`localStorage` table, completely untouched, just relabeled). They are never merged — a `localStorage` demo attempt is never shown as if it were server-persisted, and vice versa. Account-history rows link to `results.html?session=<real backend id>`, which renders via `renderBackendSession()` in `pages.js`. As of the results-honesty fix below, `results.html?id=<localStorage demo id>` now *also* delegates to that same `renderBackendSession()` whenever that local record has a real `sessionId` (i.e. it was a live, backend-tracked attempt, not a curated sample or Offline-Demo-Mode one) — see that bullet for why.
- `analytics.html` also has a "Your Account Analytics" section (Phase 10, `GET /api/analytics`), positioned **above** the sample-data sections (metrics/chart/"What Improved"/"What to Focus On Next (Sample Data)") since the analytics-honesty fix below — real aggregates (average/highest/most-recent score, completion rate, category/dimension breakdown, a progress chart reusing the existing `createChart()`), calculated server-side (`backend/analytics.py`) from the same ownership-filtered data recommendations already use.
- **Results/scoring honesty fix**: `pages.results()`'s `?id=` path used to render every completed attempt - including real backend-tracked ones - with `demoScore()`'s word-count heuristic presented as a Passed/Unsuccessful verdict and a point-change trend. It now checks `P.isLiveAttempt(a) && a.sessionId` first and, if true, delegates entirely to `renderBackendSession()` (the same honest, evaluation-aware view account-history always used) instead - never presenting the heuristic as a verdict for a real interview. An attempt with no backend session (Offline Demo Mode) shows a clearly `(simulated)`-labeled number and a "Not evaluated" badge, never a verdict or trend. The legacy local history table's Result/Change columns get the same treatment for live attempts only (`resultHTML()`/`changeForDisplay()` in `pages.js`), scoped by `P.isLiveAttempt()` (`data.js`) so the curated `a1..a8` sample dataset is untouched.
- **Dashboard account/sample separation**: `index.html` now has a real **"Your Account Overview"** section (calls `GET /api/analytics`, same data `analytics.html`'s account section already uses) above the pre-existing, now explicitly-labeled **"Sample Dashboard Preview"** section. The sample section's `#metrics`/chart/`#recent` now explicitly excludes any live attempt (`P.isLiveAttempt()`) so it is purely the fixed `a1..a8` dataset, same reasoning as the results-honesty fix above: a live attempt's word-count heuristic must never be blended into "Latest Score"/"Improvement" as if comparable to curated sample data. The account section's own "Latest Evaluated Score" and "Improvement" only ever come from real AI evaluations (`most_recent_score`/`progress`/`progress_sufficient` from `backend/analytics.py`) - an unevaluated completed interview is never shown as 0, never labeled unsuccessful, and never moves the trend.
- **Analytics account/sample separation**: same fix as the Dashboard, applied to `analytics.html`. `pages.analytics()`'s sample block (`#metrics`/chart/"What Improved"/"What to Focus On Next") now also excludes live attempts (`P.isLiveAttempt()`) and is labeled "Sample Dashboard Preview"/"(Sample Data)". The chart legend's inline SVG icons (previously hardcoded to pre-redesign light-theme hex colors, a leftover from `1d0a572`) now match the actual dark-theme chart colors.
- **Still an open, documented limitation**: `achievements.html`'s own rendering (`P.achievementState()`, driven by `P.completed()`) has the identical sample/live blending issue as the Dashboard and Analytics had - a live attempt can unlock/contribute to an achievement the same as curated sample data, with no visual distinction. Not fixed in either of those two passes; fix the same way (`P.isLiveAttempt()` filtering + explicit labeling) if asked to continue this line of work.
